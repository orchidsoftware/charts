# Матрица дизайна документации

Дата: 2026-09-06. Область: статическая документация `/docs/` как раздел
единого сайта Orchid Charts вместе с demo и Lab. Основная задача — найти метод,
прочитать объяснение и перенести пример в свой продукт. Контекст — браузер на
desktop, планшете и телефоне, клавиатура, указатель, сенсорный экран, светлая и
тёмная темы, увеличение текста.

Apple HIG задаёт приоритеты: доступность и ясность, предсказуемая навигация,
эффективность задачи, затем выражение бренда. Это адаптация принципов HIG к
веб-документации, а не утверждение о нативном интерфейсе Apple или сертификации.

Ниже — авторская оценка через опубликованные принципы десяти дизайнеров и
специалистов по проектированию интерфейсов. Они не участвовали в ревью; строки
не являются их цитатами, отзывами или личным одобрением. Числовые оценки не
используются: у каждого вывода есть наблюдаемая проблема и проверяемое изменение.

## Решение по визуальной иерархии

Одна шапка сайта → тихое меню раздела → заголовок и вводный абзац → шаги и
примеры → ссылка на исходный документ → один общий футер. Бренд сохраняется
через логотип, общую палитру, навигацию и системную типографику. Светлая
поверхность статьи обозначает область чтения так же, как поверхности карточек
обозначают графики в demo. Это решение для Orchid Charts, а не требование Apple
делать все документы белыми.

Состояния меню: обычное, hover, видимый клавиатурный фокус, текущая страница.
На mobile используется нативное раскрытие без собственного управления фокусом.
Код получает подпись языка; текст остаётся доступным для выделения и копирования
средствами браузера. Палитра подсветки адаптируется к системной теме. Фокусируемые
области кода и таблиц допускают прокрутку с клавиатуры. Уменьшение движения
отключает плавную прокрутку.

## Проверка реализации

- Генерация охватывает руководства в `docs`, включая API reference и frameworks.
  Overview и Chart types исключены из веб-навигации: `/docs/` открывает Getting
  started, а каталог типов уже находится в боковом меню и demo.
- Автотесты проверяют внутренние ссылки и якоря, подсветку, экранирование HTML,
  общую навигацию, единственный футер и отсутствие клиентских скриптов.
- Визуальная проверка: Getting started и API reference на desktop и mobile;
  общая шапка при переходе в demo; выбранный пункт, раскрытие меню и возврат наверх.
- Сборка: `npm run build:demo`; проверка кода: `npm run lint` и `npm run format:check`.

Проверено в Chromium: Getting started, API reference и frameworks при ширине
390 и 1280 px, в светлой и тёмной системных темах. Четыре браузерных сценария
проверяют отсутствие переполнения страницы, подсветку, состояние меню и один
футер. Дополнительно вручную просмотрены Getting started и API reference,
раскрыто мобильное меню и проверен локальный переход наверх. Отдельно проходят
19 существующих тестов demo и Lab.
Это экспертная эвристическая проверка, а не исследование с пользователями или
полный аудит VoiceOver, Safari и всех сочетаний настроек доступности.

## Повторное ревью: код и согласованность с лендингом

После первой переработки чтение всё ещё страдало: правило моноширинного
шрифта оставалось только в CSS лендинга, а Docs использовали браузерный
`monospace` и размер 13 px. Встроенный код дополнительно уменьшался и получал
плашку внутри предложения. Код в таблицах был мельче основного текста.
Лендинг при этом сохранял самостоятельный тёмный блок с тенью.

Исправления следуют прежним критериям HIG, Santa Maria, Rams и Frost:

- Шрифт кода перенесён в общие стили: `ui-monospace`, SFMono, Menlo, Consolas.
- Код в блоках — 15 px с интерлиньяжем 1.75; в тексте — 0.94 em без плашек,
  с основным цветом текста и умеренным весом. Таблицы используют текст 16 px,
  а сигнатуры не разбиваются посередине: при необходимости прокручивается таблица.
- У demo, Lab и Docs теперь общие правила кода: гарнитура, размер, поверхность,
  граница, радиус и цвета подсветки. Лендинг перестал использовать отдельную
  тёмную карточку кода с тенью.
- Основной текст документации увеличен до 17 px, длина строки ограничена 68ch.
  Общая шапка и подвал продолжают связывать разделы; область чтения не получает
  отдельную брендовую палитру.

Эти параметры — проверяемые решения проекта, а не приписанные дизайнерам
предпочтения и не числовые требования Apple.

## Иконки типов в меню

Решение: использовать существующие SVG из галереи только рядом с названиями
типов графиков. Это дополнительный ориентир, а не замена текста. Оценка через
те же принципы; реальные дизайнеры не голосовали за этот интерфейс.

в пользовательском исследовании. Приоритет названия и выбранного пункта
сохраняется в обеих темах.

## Inline-code в предложениях: пересмотр решения

Контрольный пример: `The download() method starts a browser download:` на
странице Exporting SVG. Предыдущего увеличения моноширинного шрифта оказалось
недостаточно: слово было почти того же цвета и веса, что окружающая фраза,
но другая ширина букв нарушала ритм чтения. Обратная связь пользователя
отменяет прежнюю гипотезу об одном моноширинном оформлении любого `<code>`.

| Критерий                     | Решение для inline-code                                                                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apple HIG — ведущий критерий | Приоритет читаемости и ясной иерархии: гарнитура, кегль и интерлиньяж предложения сохраняются; метод выделяется весом 600.                          |
| Jason Santa Maria            | Согласовать рисунок букв и базовую линию с фразой; не уменьшать вставку относительно текста.                                                        |
| Dieter Rams                  | Не превращать название метода в декоративную плашку или подобие кнопки.                                                                             |
| Jakob Nielsen                | Название должно быть заметно при сканировании, но не выглядеть интерактивным без настоящей ссылки.                                                  |
| Brad Frost                   | Разделить семантические роли: код в прозе, самостоятельный пример, сигнатура в таблице. Общая система не требует одинакового оформления всех ролей. |
| Luke Wroblewski              | На телефоне сохранить обычное течение и перенос предложения; не создавать непрерывный широкий chip.                                                 |
| Ethan Marcotte               | Наследовать размер от контейнера, чтобы вставка масштабировалась вместе с текстом.                                                                  |
| Edward Tufte                 | Одного признака выделения — веса — достаточно; не добавлять рамку, тень и отдельный цвет одновременно.                                              |
| Артемий Лебедев              | `download()` читается как часть пояснения; оформление не требует самостоятельного объяснения.                                                       |
| Andy Bell                    | Семантический `<code>` сохраняется, изменение сделано CSS; длинный идентификатор может переноситься средствами браузера.                            |
| Jeremy Keith                 | Содержание и копирование остаются обычным HTML; подсветка inline-code не требует JavaScript.                                                        |

Это авторская оценка через те же опубликованные принципы, не личные мнения
перечисленных дизайнеров. Новое правило относится к коду в абзацах, списках и
заголовках. Блоки `<pre><code>` и сигнатуры таблиц API сохраняют моноширинный
шрифт: там важны синтаксис и точное различение символов. Ссылки на методы
сохраняют подчёркивание и клавиатурный фокус.

### Мягкий фон inline-code

Следующая итерация по предложению пользователя: сохранить пропорциональную
гарнитуру и размер предложения, добавить фон из общей палитры
`--charts2-demo-surface` с 5% основного цвета текста, скругление 4 px
и поля 1 × 5 px. Примесь сохраняет различимость подложки и в тёмной теме. Без бордера и тени.
Это уточняет прежнее решение «без плашек»: используется тихая текстовая
подложка, а не самостоятельный компонент управления.

- **Apple HIG / Nielsen:** подложка помогает отличать название метода от
  обычного смыслового выделения; интерактивность по-прежнему обозначает ссылка.
- **Santa Maria / Marcotte / Bell:** кегль и интерлиньяж сохраняются; вставка
  остаётся строчной и переносится, фон корректно повторяется на каждой строке.
- **Rams / Tufte / Лебедев:** рамка и тень избыточны — фон уже выполняет работу.
- **Frost:** цвет берётся из общей системы сайта и адаптируется к теме.
- **Wroblewski / Keith:** никаких новых целей нажатия и клиентских скриптов.

Итог авторской оценки: мягкий фон — да; бордер — нет. Если настоящая ссылка
содержит код, её подчёркивание и focus-state сохраняются. При чтении проверяется
само предложение, а не изолированный красивый образец метода.

### Снижение акцента inline-code

После обратной связи сочетание полужирного начертания и подложки признано
слишком заметным при чтении. Актуальное правило заменяет предыдущие значения:
вес наследуется от предложения, фон — 4% основного цвета поверх прозрачной
основы. Так подложка не складывается с отдельным цветом surface.
Размер и цвет текста наследуются; скругление 4 px и поля 1 × 5 px сохраняются.
Для обычного абзаца код больше не полужирный, а в заголовке сохраняет его вес.

чтобы название метода оставалось частью предложения.

### Регистр заголовков и навигации

По требованию пользователя редакционный ориентир — The New York Times Manual
of Style and Usage, 5th edition. Заголовки и меню docs, demo и lab используют
Title Case: Calendar Heatmaps, Getting Started, API Reference, In Your Product.
Артикли, короткие служебные слова и сочинительные союзы внутри заголовка
сохраняют строчную букву; первое и последнее слова — прописную.
Написание брендов, классов и API сохраняется. Регистр задан в исходном тексте,
без CSS text-transform; адреса страниц и якорей не меняются.
